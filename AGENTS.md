# SharedSpace

SharedSpace хранит файлы и папки и позволяет делиться ими по ссылке или через совместный доступ.

## Структура проекта

- [frontend/src/](frontend/src/) — SPA на React и TypeScript. Точка входа в `index.tsx`, маршруты в `App.tsx`. Экраны лежат в `pages/`, общие компоненты в `components/`, HTTP-клиент в `api/`, состояние Zustand в `store/`.
- [backend/](backend/) — REST API на Go и chi. Точка входа в `cmd/api/main.go`, маршруты в `internal/server/router.go`. Доменные пакеты в `internal/`, миграции PostgreSQL в `internal/database/migrations/`, клиент MinIO в `internal/storage/`, артефакты Swagger в `docs/` внутри бэкенда.
- [docs/](docs/) — руководства по запуску, тестированию и устройству проекта. [Makefile](Makefile) и [docker-compose.dev.yml](docker-compose.dev.yml) задают локальный запуск. [.github/workflows/](.github/workflows/) содержит проверки и деплой.

## Действующий продукт

SharedSpace работает в продакшене. В ТЗ укажи, как фича встраивается в существующий сценарий и затрагивает ли опубликованный API, права доступа, данные PostgreSQL и MinIO или конфигурацию. Сохраняй работу действующих клиентов, файлов, папок и ссылок вне согласованного изменения. Проверяй новое поведение на синтетических данных, которые воспроизводят состояние до обновления. Если выпуск требует миграции, новых настроек или согласованного несовместимого изменения, опиши порядок выкладки, способ проверки после неё и восстановление при сбое.

## Работа над фичей

1. Проверь текущую ветку и рабочее дерево. Создай `feat/<краткое-название>` от согласованной базы. Если пользователь выделил ветку для этой задачи, работай в ней.
2. Уточни ожидаемый результат по запросу пользователя. Вопросы задай по тем деталям, которые влияют на поведение или приёмку и ещё не описаны.
3. Перед реализацией подготовь в корне локальный `PLAN.md`. Укажи ветку и цель, запиши короткий чек-лист действий. Для каждого пункта укажи проверяемый результат и способ проверки. Сохрани незавершённый план другой задачи перед переключением. При параллельной работе используй отдельный worktree, чтобы у каждой задачи был свой файл.
4. Покажи ТЗ пользователю и дождись его согласия. Существенное расширение объёма работы согласуй до реализации.
5. Открой [указатель скиллов](.skills/README.md) и прочитай инструкции для затронутых частей проекта. Вместе с фичей добавь или обнови тесты на новое поведение и затронутые сценарии ошибок. Обнови документацию, если изменился описанный контракт или способ работы с проектом.
6. Для небольшой фичи обычно достаточно одного коммита. Если изменений много, разбей их на несколько самостоятельных коммитов. Перед каждым коммитом просмотри индекс и исключи посторонние правки и локальный план. Линтеры, тесты и сборку запусти одним итоговым прогоном после реализации всей фичи, включая её тесты, перед ручной приёмкой. Промежуточные коммиты этого прогона не требуют. Отметь проверенные пункты в `PLAN.md`.
7. Сообщи, что сделано. Для каждой применимой проверки укажи результат («прошла», «упала» или «пропущена»), включая пропуски отдельных интеграционных тестов. Для пропуска или сбоя укажи причину и что осталось подтвердить. Когда применимые проверки пройдены, подними dev-сборку для ручной приёмки изменений поведения. Дай адрес, начальное состояние, точные шаги и ожидаемый результат. Для правок только в документации проверь изменённые документы и примеры. Для изменения API приведи воспроизводимый запрос и ожидаемый ответ. Если запуск заблокирован, укажи причину.
8. Собери обратную связь пользователя, внеси согласованные правки и повтори затронутые проверки и ручную приёмку. После приёмки `PLAN.md` можно сохранить локально или удалить. Этот файл игнорируется Git. Даже принудительно его не добавляй.

## Код и документация

- Изменяй корневой `README.md` только по прямой просьбе пользователя. Держи его кратким. Контракты API, подробности разработки, настройки и сценарии проверки описывай в `docs/`.
- Пиши код без новых поясняющих комментариев. Передавай смысл через имена, структуру и тесты. Допустимы обязательные для инструментов аннотации и директивы, например Swagger и Go build tags.

## Проверки

Перед работой сверь список команд и зависимостей с текущими workflow. После реализации фичи запусти применимые проверки из указанных каталогов. Если проверка упала, исправь причину и повтори её и те проверки, на которые повлияла правка.

Запускай применимые линтеры, проверку форматирования, тесты и сборку. Исправляй ошибки и предупреждения, которые относятся к задаче, и повторяй затронутые проверки. Не отключай правила, не добавляй исключения и не пропускай проверки, чтобы скрыть найденные проблемы. Существовавшие раньше замечания вне задачи и технические блокировки указывай явно в отчёте с результатом проверки и причиной.

GitHub Actions может запустить проверки при отправке изменений или обновлении PR. Держи промежуточные коммиты локально. Выполняй `git push` и открывай PR по запросу пользователя после итогового прогона. Учитывай, что отправка изменений в `main` запускает деплой.

| Изменение | Что запустить |
| --- | --- |
| Фронтенд, [frontend.yml](.github/workflows/frontend.yml) | В `frontend/` выполни `npm install` на Node.js 22, затем `npm run lint` и `npm run format:check`. |
| Фронтенд, локально | Из `frontend/` запусти `npm test -- --watchAll=false`. Для изменений, влияющих на сборку, запусти `npm run build`. |
| Бэкенд, [backend.yml](.github/workflows/backend.yml) | В `backend/` выполни `make lint` и `go test ./...` на Go 1.26. Подготовь MinIO и ffmpeg как в CI. Для затронутых интеграционных сценариев выполни дополнительные проверки из [скилла бэкенда](.skills/backend-development/SKILL.md). Сгенерируй Swagger через `make swagger` со `swag` v1.16.6, проверь diff и включи ожидаемые изменения в коммит. CI проверяет чистоту `backend/docs/` после повторной генерации. |
| Документация и инструкции | Проверь пути, ссылки, примеры и команды по файлам проекта. Запусти `git diff --check`. |

Для dev-сборки подготовь локальный `.env` по `.env.example`. `make dev` собирает и запускает Compose, Проверь состояние сервисов через `make dev-ps`, ответ API через `curl -fsS http://localhost:8080/health` и открытие фронтенда в браузере. Для сценариев регистрации и сброса пароля возьми ссылку из логов бэкенда по инструкции в README. Фронтенд доступен на `http://localhost:3000`, API на `http://localhost:8080/api/v1`, Swagger UI на `http://localhost:8080/swagger/`. Подробнее в [руководстве по запуску](README.md) и [документации по тестам](docs/testing.md).
